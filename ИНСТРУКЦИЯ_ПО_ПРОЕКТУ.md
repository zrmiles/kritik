# Проектный практикум: сервис отзывов на видеоигры

Рабочая инструкция для команды. Основа — «Задание проектный практикум (2).pdf» (13 страниц). Номера страниц ниже позволяют быстро сверить формулировки с исходным заданием. В документе явно разделены **требования задания**, **решения для нашего проекта** и **рекомендации**.

## 1. Что нужно сдать

Работающий сервис, в котором пользователь может зарегистрироваться и войти, найти игру, добавить её в личный список, написать и изменить рецензию, поставить оценку и увидеть среднюю оценку сообщества. Каталог получает сведения об играх из внешнего API; поиск, сочетание фильтров и сортировка работают с реальными данными.

**Обязательно по заданию** (с. 1, 9–10):

- Git с понятной историей работы каждого участника и грамотным ведением репозитория.
- Работа по гибкой методологии: задачи, планирование, короткие встречи, демонстрации результата и ретроспективы.
- `README.md` с описанием проекта, технологическим стеком и точной инструкцией запуска.
- CRUD-операции, аутентификация и хотя бы одна нетривиальная задача. Для темы агрегатора названы сложные фильтры/сортировки и получение данных об играх из внешнего API (RAWG приведён как пример).
- Финальное демо и защита с реальным показом работающих сценариев.

**Важно:** задание не предписывает конкретный язык, фреймворк, БД, провайдера игрового API, способ авторизации и календарные сроки. Примеры вроде Django, React, PostgreSQL, Docker и Yandex Cloud — варианты реализации, а не обязательный набор. Роли для 3 и 4 человек в PDF также даны как примеры (с. 3–4).

## 2. Текущее состояние проекта

Реализована рабочая версия сервиса (подробности — в `README.md` и `docs/`):

- backend на Django + DRF: регистрация и вход (JWT с refresh-cookie), каталог с поиском, совместными фильтрами и сортировками, CRUD рецензий с пересчётом средней оценки, личный список, импорт из RAWG с журналом запусков;
- frontend в `frontend/`: одностраничный интерфейс, связанный с API, адаптивный, светлая/тёмная тема;
- 33 автотеста, Ruff, GitHub Actions (тесты на PostgreSQL), Docker и docker compose;
- документация: `docs/api.md`, `docs/architecture.md`, `docs/backlog.md`, `docs/testing.md`, `docs/process.md`.

Остаётся за командой: получить ключ RAWG и импортировать реальный каталог, провести опрос пользователей, вести доску задач, протоколы и отчёты, распределить роли в README, задеплоить сервис и подготовить презентацию.

## 3. Границы первой рабочей версии

Ниже — конкретизация темы для команды, чтобы было понятно, что именно проверять на демо. Детали, которых нет в PDF, помечены как **решение команды** и могут быть изменены до начала разработки, если изменения записаны в бэклоге и README.

| Возможность | Минимальное поведение и критерий готовности |
| --- | --- |
| Аккаунт | Регистрация, вход и выход. Неавторизованный посетитель может смотреть каталог, но для личного списка и написания отзыва должен войти. После перезагрузки сервер узнаёт пользователя по выбранному механизму авторизации. |
| Каталог | Список игр с названием, обложкой при наличии, годом, жанрами, платформами, рейтингом и числом отзывов. Страница игры показывает сведения и рецензии. Пустые и отсутствующие поля выводятся корректно. |
| Поиск и фильтры | Поиск по названию; одновременно применяются жанр, платформа и год выпуска. При изменении одного фильтра остальные сохраняются. Доступны сортировки по рейтингу, числу отзывов и дате выпуска. Результат и число найденных игр согласованы. |
| Личный список | Пользователь добавляет игру и удаляет её из своего списка. После повторного входа список сохраняется. Чужой список недоступен для изменения. |
| Рецензии и оценки | Авторизованный пользователь создаёт, читает, редактирует и удаляет **свою** рецензию с числовой оценкой. Другие пользователи видят её, но не могут менять. После создания, изменения и удаления пересчитываются средняя оценка и количество отзывов. |
| Игры и внешний API | Сервис получает сведения об играх от выбранного внешнего API, сохраняет/обновляет их в БД и показывает источник данных. Повторная загрузка не плодит дубликаты. При недоступности провайдера каталог из уже сохранённых игр продолжает открываться, а ошибка импорта видна ответственному участнику. |
| Управление данными | Нужен полный CRUD хотя бы для рецензий. Для игр предусмотрите создание/редактирование/удаление администратором **или** опишите и покажите, как CRUD закрывается другими объектами проекта; импортируемые игры не должны бесконтрольно меняться обычным пользователем. |

**Решения команды, которые нужно зафиксировать до кода:** шкала оценок (в проекте выбрано 1–10), может ли один пользователь оставить несколько рецензий на игру (для первой версии лучше одну), как считается среднее и округление, какие поля приходят из внешнего API, кто и как запускает импорт. Это не заданные извне ограничения. Для пустого набора отзывов показывайте «Нет оценок», а не `0/10`.

Не обязательны для первой версии: лайки, рекомендации, социальная сеть, уведомления, платные функции, модерация текстов и аналитика кликов. Берите их только после готовности основных сценариев.

## 4. Практический порядок работы

### Шаг 1. Зафиксировать продукт и команду

1. Запишите в бэклоге, для кого сервис и какую проблему он решает: например, выбрать игру по впечатлениям сообщества и сохранить кандидатов в личный список.
2. Проведите короткий опрос потенциальных пользователей и посмотрите аналоги. Для роли Product Manager в задании указан мини-опрос из 3–5 вопросов и анализ конкурентов (с. 2, 6); сохраните реальные ответы и выводы.
3. Назначьте ответственных за продукт, архитектуру, интерфейс, качество/релиз и процесс. Один человек может совмещать роли. В таблице задач у каждой работы должен быть исполнитель.
4. Согласуйте решения из раздела 3 и критерии приёмки для каждой истории до начала реализации.

**Результат шага:** краткое описание продукта, список участников и ролей, приоритизированный бэклог, 5–10 пользовательских историй с проверяемыми критериями приёмки (с. 6).

### Шаг 2. Оформить репозиторий и архитектуру

1. Настройте Git: основная ветка, отдельные ветки задач, осмысленные коммиты и просмотр изменений перед слиянием. Не коммитьте API-ключи, пароли, `.env`, виртуальные окружения, БД и сгенерированные зависимости.
2. Выберите стек. **Рекомендуемый путь для этой папки:** сохранить имеющийся HTML/CSS/JS как старт интерфейса, сделать сервер на Django + Django REST Framework, БД PostgreSQL и импорт из RAWG API. Это предложение, а не требование PDF. Если команда выбирает иной стек, запишите причины и точные команды запуска.
3. Нарисуйте схему: браузер → API → БД; отдельный модуль импорта → внешний игровой API → БД. Покажите, где находятся авторизация, расчёт рейтинга и фильтрация.
4. Спроектируйте данные и API до параллельной разработки. Минимальные сущности: `User`, `Game`, `Review`, `SavedGame`; связь рецензии и сохранённой игры с автором и игрой; уникальный внешний ID игры. При решении «один отзыв на игру от автора» добавьте соответствующее уникальное ограничение в БД.

**Результат шага:** схема архитектуры и БД, описание API, начальный `README.md`, задачи по компонентам. В PDF схема и API названы артефактами технического лидера (с. 5–6).

### Шаг 3. Сделать вертикальный рабочий сценарий

Сначала доведите один путь до конца: регистрация → каталог из БД → страница игры → создание рецензии → изменение рейтинга → сохранение игры → повторный вход и проверка сохранения данных. Затем добавьте редактирование/удаление, фильтры, сортировки и импорт. Так команда раньше увидит ошибки в связке интерфейса, API и БД.

**Предлагаемый контракт API** (можно изменить, но зафиксировать до интеграции):

| Запрос | Назначение |
| --- | --- |
| `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout` | Аккаунт и сессия/токен. |
| `GET /api/games`, `GET /api/games/{id}` | Каталог и игра; параметры поиска, фильтров, сортировки и пагинации. |
| `GET /api/games/{id}/reviews` | Рецензии игры. |
| `POST /api/reviews`, `PATCH /api/reviews/{id}`, `DELETE /api/reviews/{id}` | Создание, изменение и удаление собственной рецензии. |
| `GET /api/me/saved-games`, `POST /api/me/saved-games`, `DELETE /api/me/saved-games/{game_id}` | Личный список. |
| Административная команда/эндпоинт импорта | Загрузка или обновление игр из внешнего источника. |

На сервере проверяйте права доступа, допустимость оценки и текста отзыва, существование игры и повторное добавление. Не полагайтесь только на ограничения формы в браузере. Секрет внешнего API храните в переменной окружения; опишите получение ключа и пример конфигурации без настоящего ключа. Если условия выбранного API ограничивают хранение изображений или атрибуцию, соблюдайте их и укажите источник на сайте.

### Шаг 4. Проверить и выпустить

1. Автоматизируйте проверки ключевой логики: права на изменение/удаление отзывов, пересчёт среднего после CRUD, сочетание фильтров и порядок сортировки, повторный импорт без дубликатов, поведение при ошибке внешнего API.
2. Пройдите вручную сценарии в браузере на узком и широком экранах. Проверьте пустой каталог, отсутствие результатов, ошибку входа, ошибку импорта, страницу без отзывов и долгие тексты.
3. Настройте автоматический запуск проверок при изменениях, если команда использует CI. Подготовьте воспроизводимый запуск для преподавателя: миграции БД, переменные окружения, создание тестовых данных/импорт, команды сервера и адрес приложения.
4. Покажите работающий сервис преподавателю. В задании для DevOps/QA приведены CI/CD, деплой и работающий адрес как ожидаемые артефакты роли (с. 8–9). Если внешний сервер недоступен, заранее согласуйте с преподавателем формат демонстрации; не заменяйте живой сервис статическим макетом без пояснения.

**Результат шага:** прошедшие тесты, чек-лист ручной проверки, инструкция запуска, рабочее демо и известные ограничения.

## 5. Как вести задачи и встречи

Используйте доску задач (в PDF упомянута «Ёжка») или другой доступный команде инструмент. Для каждой задачи запишите владельца, приоритет, срок, критерий готовности и ссылку на код/результат. Статусы: «Запланировано» → «В работе» → «На проверке» → «Готово»; заблокированные задачи отмечайте отдельно.

- В начале недельного цикла — планирование спринта и оценки задач. В течение недели — короткие стендапы о сделанном, следующем шаге и блокировках. В конце — просмотр кода, тестирование, демо и ретроспектива. Это соответствует примеру недельного цикла в PDF (с. 9).
- Менеджер проекта контролирует сроки и риски, продуктовый менеджер решает приоритет функций, технический лидер отвечает за архитектуру и код-ревью. Если роли совмещены, обязанности всё равно записываются явно (с. 1–8).
- Ведите реальные протоколы встреч, бэклог, историю изменений и отчёты. Не создавайте фиктивную активность задним числом.

**Отчёт на практическом занятии за прошедшие две недели** должен содержать шесть пунктов из задания (с. 11): достижения; что не выполнено и почему; план на следующую неделю; проблемы и блокировки; вклад каждого участника; метрики и артефакты. В PDF также показан пример еженедельного отчёта менеджера проекта (с. 7–8); используйте его как формат промежуточного обновления.

## 6. Распределение работы

Это карта ответственности, а не требование иметь ровно столько участников.

| Зона | Конкретная работа для сервиса | Что показать |
| --- | --- | --- |
| Технический лидер / backend | Схема БД, авторизация, API игр и отзывов, права доступа, расчёт рейтинга, код-ревью. | Диаграмма, спецификация API, коммиты и просмотр изменений. |
| Product Manager / frontend | Исследование пользователей, приоритеты, истории, интерфейс каталога и рецензий, интеграция с API. | Бэклог, критерии приёмки, результаты мини-опроса, работающий пользовательский сценарий. |
| Project Manager / frontend | Планирование, встречи, сроки и отчёты; типовые интерфейсные элементы, адаптивность. | Доска спринта, протоколы, отчёты, адаптивные страницы. |
| QA / DevOps / backend | Импорт из внешнего API, тесты, учёт дефектов, автоматические проверки, запуск и релиз. | Тесты и чек-листы, результаты CI, инструкция запуска, доступное демо. |

Для команды из **трёх** человек функции PM и аналитика распределяются между техническим лидером и Product Manager; третий участник совмещает QA/DevOps и часть backend. Для команды из **четырёх** человек отдельный Project Manager берёт процесс и часть frontend. Эти схемы предложены в PDF (с. 3–5). При ином составе распределите все зоны без пропусков.

## 7. Готовность к защите

Проверьте `README.md`: назначение сервиса, стек и версии, требования к окружению, пример переменных, настройка БД, миграции, импорт/тестовые данные, запуск backend и frontend, запуск тестов, адрес демо, состав команды, ограничения проекта. Команды должны работать на чистой машине или в заранее описанном окружении.

В презентации раскройте все пункты структуры из PDF (с. 11–12): проблема и её актуальность; решение и функции; технология и архитектура; аудитория, конкуренты и отличие; возможная бизнес-модель; живое демо; команда и вклад каждого; измеримые результаты; план развития; заключение. Бизнес-модель здесь — часть защиты, а не требование встроить оплату в сервис.

Для каждого участника укажите роль, выполненные задачи, реализованный модуль и технологии; каждый должен показать свою часть и ответить на вопросы по ней. Полезно подготовить приложение к презентации со ссылками на задачи, коммиты, код-ревью и тесты (с. 12–13).

**Временные рамки защиты из задания:** 15 минут на доклад и 5–7 минут на вопросы. Рекомендовано 12–14 слайдов (с. 13). Заранее отрепетируйте показ без подмены реальных данных демонстрационными: регистрация/вход → фильтрация каталога → игра → отзыв и изменение среднего рейтинга → личный список → повторный вход → краткий показ импорта/его результата.
