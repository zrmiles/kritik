## 1. Операция

### 1.1. Что описывается

Запрос к HTTP API приложения, которым пользователь публикует рецензию на игру: оценку от 1 до 10 и короткий текст. Это единственный способ создать рецензию. Форма на странице игры в браузере вызывает именно эту операцию, а другой клиент (мобильное приложение, скрипт, автотест) может вызвать её так же.

| | |
| --- | --- |
| Тип интерфейса | HTTP API (REST, JSON), Django REST Framework |
| Метод и адрес | `POST /api/reviews/` |
| Назначение | Сохранить рецензию вошедшего пользователя на выбранную игру и сразу пересчитать оценку сообщества этой игры |
| Сценарий | [US-5. Публикация рецензии](01-requirements.md#us-5-публикация-рецензии--fr-4--ключевой) (ключевой) |
| Требование | [FR-4](01-requirements.md#21-требования-к-функционалу): одна рецензия на игру с оценкой 1–10 и текстом 10–500 символов, оценка сообщества сразу пересчитывается |
| Ограничения | [NFR-3](01-requirements.md#22-ограничения): операция доступна только с access-токеном, автором рецензии всегда становится владелец токена |
| Состояние | ✅ реализовано и покрыто автотестами. В ходе ЛР 3 исправлено расхождение с US-5: два одновременных запроса на одну игру давали `500` вместо `400` (см. [раздел 2.5](#25-характерная-ошибка-повторная-рецензия)) |

Изменение и удаление своей рецензии (`PATCH` и `DELETE /api/reviews/{id}/`, сценарий US-6) в этот контракт не входят и кратко описаны в [docs/api.md](api.md#рецензии).

## 2. Контракт

### 2.1. Кто вызывает и как

**Кто вызывает.** Клиент, действующий от имени зарегистрированного пользователя: веб-интерфейс «Критика» (кнопка «Опубликовать» на странице игры) или любой HTTP-клиент. Гость вызвать операцию не может.

**Запрос.**

```http
POST /api/reviews/ HTTP/1.1
Host: localhost:8000
Authorization: Bearer <access-токен>
Content-Type: application/json
Accept: application/json

{"game_id": 19, "score": 9, "text": "Душная, но гениальная игра про чуму и выбор."}
```

| Заголовок | Обязателен | Значение |
| --- | --- | --- |
| `Authorization` | да | `Bearer <access>`, где `access` — JWT из ответа `POST /api/auth/register/`, `/login/` или `/refresh/` |
| `Content-Type` | да | `application/json`. Форма `application/x-www-form-urlencoded` тоже принимается, но интерфейс её не использует |
| `Accept` | нет | `application/json`; ответ всегда в JSON |

CSRF-токен и cookie для этой операции не нужны: пользователь определяется только по заголовку `Authorization`.

**Как получить access-токен.** Вход (`POST /api/auth/login/`) или регистрация (`POST /api/auth/register/`) возвращают поле `access`. Эти два запроса, в отличие от публикации рецензии, защищены от CSRF: сначала нужно получить cookie `csrftoken` запросом `GET /api/auth/csrf/` и передать её значение в заголовке `X-CSRFToken` (см. [пример 1](#пример-1--успешная-публикация)). Access-токен действует **5 минут** (`access_expires_in: 300`). Когда он истёк, клиент получает `401` и продлевает его запросом `POST /api/auth/refresh/` с cookie `kritik_refresh`, полученной при входе; так делает веб-интерфейс.

### 2.2. Входные данные

Тело запроса — JSON-объект с тремя обязательными полями.

| Поле | Тип | Обязательно | Допустимые значения | Примечание |
| --- | --- | --- | --- | --- |
| `game_id` | целое число | да | `id` игры, которая есть в каталоге | `id` берётся из `GET /api/games/` (`results[].id`) или из адреса страницы игры `#/game/<id>`. Строка из цифр (`"19"`) тоже принимается |
| `score` | целое число | да | от **1** до **10** включительно | Строка `"9"` принимается как 9. Дробное значение (`8.5`) — ошибка |
| `text` | строка | да | от **10** до **500** символов | Пробелы и переводы строк в начале и в конце отбрасываются **до** проверки длины: `"   ок   "` — это 2 символа. Символы считаются как буквы, а не байты: кириллица и эмодзи — по одному символу |

Другие поля в теле (`id`, `author`, `created_at` и т. п.) игнорируются: автора и даты сервер проставляет сам.

**Условия вызова.**

1. Пользователь вошёл в аккаунт и access-токен не истёк.
2. Игра с `game_id` существует.
3. У этого пользователя ещё **нет** рецензии на эту игру. Изменить существующую можно только запросом `PATCH /api/reviews/{id}/`.

Операция **не идемпотентна**: повторная отправка того же запроса не создаёт вторую рецензию, а возвращает ошибку из раздела 2.5.

**Порядок проверок.** Сначала проверяется токен (`401`), затем поля по отдельности (`400` с ошибками по каждому неверному полю сразу), и только если все поля верны — нет ли уже рецензии на эту игру (`400` по `game_id`).

### 2.3. Результат успешного вызова

Код **`201 Created`**, тело — JSON-объект созданной рецензии.

| Поле | Тип | Значение |
| --- | --- | --- |
| `id` | целое число | Идентификатор рецензии. Нужен для `PATCH` и `DELETE /api/reviews/{id}/` |
| `author` | строка | Публичное имя автора: «Имя на сайте», а если оно не задано — логин |
| `is_owner` | логическое | Всегда `true`: рецензию создал владелец токена |
| `score` | целое число | Оценка, 1–10 |
| `text` | строка | Текст без пробелов по краям, в том виде, в каком он сохранён |
| `created_at`, `updated_at` | строка | Время создания и изменения в ISO 8601 со смещением часового пояса `Europe/Moscow`, например `2026-11-17T00:18:03.177599+03:00`. Сразу после создания отличаются на микросекунды |

`game_id` в ответе **не возвращается**: вызывающая сторона его уже знает.

**Что меняется в системе.**

- В БД появляется запись рецензии с автором — владельцем токена.
- Сразу, без кэша, меняются данные игры в `GET /api/games/{game_id}/`: `average_rating` (строка с двумя знаками после точки, например `"7.75"`), `review_count` (+1) и `score_distribution` (массив из 10 чисел, элемент с индексом `score − 1` увеличивается на 1).
- Рецензия появляется первой в `GET /api/games/{game_id}/reviews/` и в `GET /api/me/reviews/`, а поле `reviews` в `GET /api/games/stats/` увеличивается на 1.

### 2.4. Формат ошибок

| Код | Тело | Когда |
| --- | --- | --- |
| `400 Bad Request` | Объект «поле → список сообщений»: `{"<поле>": ["<сообщение>", …]}`. Если неверных полей несколько, в объекте все они | Неверные или недостающие данные, повторная рецензия |
| `401 Unauthorized` | `{"detail": "<сообщение>"}`, для неверного или истёкшего токена ещё `"code": "token_not_valid"` | Нет токена, токен неверный или истёк |
| `405 Method Not Allowed` | `{"detail": "Метод \"GET\" не разрешен."}` | Любой метод, кроме `POST` и `OPTIONS` |

Тексты сообщений — на русском (`LANGUAGE_CODE = ru-ru`), их можно показывать пользователю как есть. Программно ошибку нужно распознавать по **коду ответа и имени поля**, а не по тексту.

### 2.5. Характерная ошибка: повторная рецензия

Пользователь пытается опубликовать вторую рецензию на игру, на которую уже писал: нажал «Опубликовать» дважды, отправил форму из второй вкладки или клиент повторил запрос после обрыва связи.

| | |
| --- | --- |
| Код ответа | **`400 Bad Request`** |
| Тело | `{"game_id": ["Вы уже оставили рецензию на эту игру."]}` |
| Как распознать | Код `400` и ключ `game_id` в теле, при этом других ключей нет |
| Что происходит в системе | Ничего: вторая рецензия не создаётся, первая не изменяется, оценка сообщества и число рецензий те же |
| Что делать вызывающей стороне | Показать сообщение у формы. Чтобы изменить уже написанную рецензию, найти её `id` в `GET /api/me/reviews/` (элемент, у которого `game.id` равен `game_id`) и вызвать `PATCH /api/reviews/{id}/` |

Ответ одинаковый и при последовательных, и при **одновременных** запросах. До ЛР 3 одновременные запросы проходили проверку в `validate()` вместе, вставка второго нарушала ограничение `unique_review_author_game` в БД, и клиент получал `500`. Теперь это нарушение тоже превращается в `400` с тем же телом. Проверено: 8 параллельных запросов на одну игру дают один `201` и семь `400`.

Ошибка с тем же кодом `400` и ключом `game_id`, но **другим** текстом означает неверный `game_id`, а не повтор (см. таблицу ниже).

### 2.6. Остальные ошибки (справочно)

Ответы получены на чистой базе с демо-каталогом 17.11.2026.

| Что передано | Код | Тело ответа |
| --- | --- | --- |
| Без заголовка `Authorization` | `401` | `{"detail": "Учетные данные не были предоставлены."}` |
| Неверный или истёкший токен | `401` | `{"detail": "Given token not valid for any token type", "code": "token_not_valid", "messages": [...]}` |
| Пустой объект `{}` | `400` | `{"game_id": ["Это поле обязательно."], "score": ["Это поле обязательно."], "text": ["Это поле обязательно."]}` |
| `"game_id": 9999` (такой игры нет) | `400` | `{"game_id": ["Недопустимый первичный ключ \"9999\" - объект не существует."]}` |
| `"game_id": "abc"` | `400` | `{"game_id": ["Некорректный тип. Ожидалось значение первичного ключа, получен str."]}` |
| `"score": 11` / `"score": 0` | `400` | `{"score": ["Убедитесь, что это значение меньше либо равно 10."]}` / `["… больше либо равно 1."]` |
| `"score": 8.5` | `400` | `{"score": ["Введите правильное число."]}` |
| `"text": "Ок"` | `400` | `{"text": ["Убедитесь, что это значение содержит не менее 10 символов (сейчас 2)."]}` |
| `"text"` из 501 символа | `400` | `{"text": ["Убедитесь, что это значение содержит не более 500 символов (сейчас 501)."]}` |

Ошибки `400` и `401` ничего не меняют в системе.

## 3. Примеры

Примеры выполнены на чистой базе: `docker compose up --build` (миграции и демо-каталог загружаются автоматически) или без Docker — `python manage.py migrate && python manage.py seed_demo` и `runserver`. Адрес — `http://localhost:8000`. Перед примерами в каталоге у игры **«Мор (Pathologic 2)»** (`id = 19`) 3 рецензии с оценками 3, 9 и 10, `average_rating` равен `"7.33"`.

**Подготовка: получить access-токен пользователя `anna`.** Пользователь создаётся регистрацией из сценария US-1, ответ сразу содержит токен. Если `anna` уже есть, замените адрес `register/` на `login/` и уберите из тела `display_name` и `password_confirm`.

```bash
curl -s -c jar -o /dev/null http://localhost:8000/api/auth/csrf/
CSRF=$(awk '$6 == "csrftoken" {print $7}' jar)
TOKEN=$(curl -s -b jar -c jar -H "X-CSRFToken: $CSRF" -H "Content-Type: application/json" \
  -d '{"username": "anna", "display_name": "Анна", "password": "Kritik-2026!", "password_confirm": "Kritik-2026!"}' \
  http://localhost:8000/api/auth/register/ | python3 -c 'import sys, json; print(json.load(sys.stdin)["access"])')
```

Токен действует 5 минут; если пример выполняется позже, повторите подготовку с `login/`.

### Пример 1 — успешная публикация

Пользователь `anna` (имя на сайте «Анна») публикует первую рецензию на «Мор (Pathologic 2)»: оценка **9**, текст из 44 символов.

```bash
curl -s -i http://localhost:8000/api/reviews/ \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"game_id": 19, "score": 9, "text": "Душная, но гениальная игра про чуму и выбор."}'
```

Ожидаемый ответ:

```http
HTTP/1.1 201 Created
Content-Type: application/json

{
  "id": 62,
  "author": "Анна",
  "is_owner": true,
  "score": 9,
  "text": "Душная, но гениальная игра про чуму и выбор.",
  "created_at": "2026-11-17T00:18:03.177599+03:00",
  "updated_at": "2026-11-17T00:18:03.177608+03:00"
}
```

`id` равен 62 на чистой базе (в демо-каталоге 61 рецензия), время — момент запроса.

Проверка результата: `curl -s http://localhost:8000/api/games/19/` возвращает

```json
{"id": 19, "title": "Мор (Pathologic 2)", "average_rating": "7.75", "review_count": 4,
 "score_distribution": [0, 0, 1, 0, 0, 0, 0, 0, 2, 1], "...": "..."}
```

Оценка сообщества стала (3 + 9 + 10 + 9) / 4 = 7,75 (на странице «7,8»), рецензий 4, столбец «9» гистограммы вырос с 1 до 2. Так и описано в сценарии US-5.

### Пример 2 — повторная рецензия на ту же игру

Сразу после примера 1 тот же пользователь отправляет ещё одну рецензию на «Мор» с другой оценкой.

```bash
curl -s -i http://localhost:8000/api/reviews/ \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"game_id": 19, "score": 8, "text": "Вторая попытка написать рецензию на Мор."}'
```

Ожидаемый ответ:

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json

{"game_id": ["Вы уже оставили рецензию на эту игру."]}
```

Проверка результата: `GET /api/games/19/` по-прежнему возвращает `"average_rating": "7.75"` и `"review_count": 4`, а в `GET /api/me/reviews/` у `anna` одна рецензия на эту игру — с оценкой 9 из примера 1.
